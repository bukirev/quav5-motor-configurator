# 2026-11-20 — Конфигуратор маппинга моторов для ArduCopter

## Задача

Пользователь: «разработать приложение, которое будет как конфигуратор настраивать
правильный мапинг моторов и всё что нужно»; сначала — исследование стандартов
и проверка надёжности. Приложенный пример (`motor_map_tool.py`) — рабочий
прототип, но маппинг в нём сделан неверно. Указана папка с прошивкой:
`C:\Trading\!!!\QUAV5+\CUAVv5`.

## Уточнения, полученные от пользователя

| Вопрос | Ответ |
|---|---|
| На каком автопилоте делаем | ArduCopter 4.7.2 — плата перепрошита в ArduPilot |
| Геометрия рамы | верхний передний правый — против часовой, нижний передний правый — по часовой (пара на луче вращается встречно) |
| Как применять настройки | оба режима: прямая запись с бэкапом и readback + экспорт `.params` |

Рама: 8 моторов, 4 луча в компоновке квадро-X, по 2 мотора на луч (верхний/нижний).

## Что установлено по факту

1. **Прошивка.** `C:\Trading\!!!\QUAV5+\CUAVv5\firmware-version.txt` →
   `4.7.2-FIRMWARE_VERSION_TYPE_OFFICIAL`; `git-version.txt` → commit
   `fb773567896014da007bca58358704d4a0d8516f`, `APMVERSION: ArduCopter V4.7.2`.
   В `arducopter.elf` найдены строки `ArduCopter V4.7.2 (fb773567)` и `CUAVv5`.
   **Плата CUAV V5+, прошивка ArduCopter 4.7.2.**
2. **Расхождение с предыдущей сессией.** 2026-10-26 на плате был **PX4**
   (снимок `configs/px4_params_COM18_20261026-172517.params`: `SYS_AUTOSTART=12001`,
   `CA_ROTOR_COUNT=8`, `PWM_MAIN_FUNC1..8=101..108`). Значит плату перепрошили
   в ArduPilot; пример из задания написан под ArduPilot и по смыслу подходит,
   но в нём неверная модель маппинга.
3. **Модель маппинга в ArduPilot** (из исходников 4.7.2):
   * функция мотора: `SRV_Channel.h:82` → `k_motor1 = 33` (M1…M8 → 33…40);
   * назначение на выход: `SERVOx_FUNCTION`;
   * позиция и направление вращения: таблица рамы в `AP_MotorsMatrix.cpp`
     (`setup_octaquad_matrix`, строка 973; тип X — строка 993);
   * наша рама = `FRAME_CLASS=4` (OCTAQUAD) + `FRAME_TYPE=1` (X). Класса
     «OctoCoax» в 4.7.2 нет: `CoaxCopter` (9) — это вертолет с двумя моторами.
4. **Тест мотора.** `MAV_CMD_DO_MOTOR_TEST` (209): param1 — номер мотора,
   param2 — тип значения (0 = процент), param3 — значение, param4 — таймаут,
   param5 — число моторов в последовательности. В 4.7.2 `COMMAND_LONG`
   конвертируется в `COMMAND_INT` (`param5 → x`), поэтому `param5` доходит как
   `motor_count` (`GCS_MAVLink_Copter.cpp:734`).
5. **Запись параметров.** `PARAM_SET`; тип значения в сообщении игнорируется,
   тип берётся из самого параметра, значение приходит float32, подтверждение —
   эхо `PARAM_VALUE` (`GCS_Param.cpp:265`).

Подробности с ссылками на строки исходников — в
`../docs/MOTOR_MAPPING_ARDUPILOT_4.7.2.md`.

### Принципы, заложенные в приложение

* Измерение, а не догадка: направление и место мотора определяются тестом мотора
  и отметкой пользователя на виде сверху; приложение само считает, какая функция
  должна стоять на каком выходе.
* Проверка коаксиальных пар: одинаковое направление на луче — ошибка
  (момент по yaw не гасится). Коррекция через `SERVOx_REVERSED` предлагается
  явно и только по флажку пользователя.
* Любая запись: сначала полный бэкап параметров в `configs/`, затем запись,
  затем readback каждого параметра, затем отчёт «было → стало → основание → проверка».
* Безопасность: тест мотора — только по явной команде, только с подтверждением
  «пропеллеры сняты», отдельная кнопка СТОП, предусловия ArduPilot
  (на земле, safety switch в Safe, RC откалиброван, disarm) выведены в интерфейсе.

### Найденные и исправленные ошибки по ходу работы

* `COMMAND_LONG` упаковывался по неверной структуре (`<7fHHBBB` вместо
  `<fffffffHBBB`) — поймано кросс-проверкой с pymavlink.
* Декодирование целочисленных параметров читало байты union'а; ArduPilot
  передаёт число во float32. Исправлено с запасным вариантом.
* Логика распределения моторов не умела предложить `SERVOx_REVERSED`, когда
  на луче оба мотора крутятся одинаково. Переработана.
* **Тест мотора отправлял номер мотора вместо номера теста** — найдено при
  сверке со спецификацией пользователя (см. ниже), исправлено.

### Сверка со спецификацией пользователя (2026-11-20, файл `ardupilot_4_7_octoquad_x_agent_spec.md`)

Спецификация проверена по трём независимым источникам: исходники ArduPilot
(тег `Copter-4.7.2` побайтово совпадает с commit `fb773567`), официальная схема
`m_04_01_octo_quad_x.svg` на ardupilot.org и официальные тексты.

Подтверждено:

| Утверждение спецификации | Результат |
|---|---|
| `FRAME_CLASS=4` (OctaQuad) + `FRAME_TYPE=1` (X) | подтверждено (`ArduCopter/Parameters.cpp:683`, `AP_Motors_Class.h`) |
| Таблица моторов (угол, направление, порядок) | подтверждено (`AP_MotorsMatrix.cpp:993-1006`) |
| Пары FR(1,6), FL(2,5), RL(3,8), RR(4,7) с встречным вращением | подтверждено |
| `param1` теста — **номер теста, а не номер мотора** | подтверждено (`AP_MotorsMatrix.cpp:466-470`, `motor_test.cpp:91,188`) |
| Порядок теста A–H = [1,6,4,7,3,8,2,5] | подтверждено по официальной схеме: A=M1, B=M6, C=M4, D=M7, E=M3, F=M8, G=M2, H=M5 |
| `param6` (порядок обхода) в 4.7.2 не используется | подтверждено (`GCS_MAVLink_Copter.cpp:734-745`: используется `packet.x` = param5 как motor_count) |
| Функция мотора N = 32 + N | подтверждено (`SRV_Channel.h:82`) |
| `SERVOx_REVERSED=1` инвертирует импульс и разворачивает мотор | подтверждено (`SRV_Channel.cpp:192-194`: `scaled_value = high_out - scaled_value`) |
| Co-rotating X8 — `FRAME_CLASS=17` + скрипт `X8-corotating.lua` | подтверждено (текст ardupilot.org, раздел OCTO QUAD FRAMES) |
| Ярусы: M1–M4 верхние, M5–M8 нижние | подтверждено по официальной схеме (`layer-numbers-top` / `layer-numbers-bottom`) |

Расхождения:

1. **В спецификации есть внутреннее противоречие:** в разделе 3.1 сказано, что
   `param1` — это порядковый номер теста (и это верно), а в разделе 6.1 — «param1 =
   номер мотора 1..8». Верным является первый вариант; в коде приложения
   использовался второй — исправлено.
2. **Утверждение «параметры хранятся в RAM до перезагрузки» (раздел 6.4)
   неверно.** `PARAM_SET` сразу пишет во flash: `vp->save(force_save)`
   (`GCS_Param.cpp:315-318`). Неверный маппинг переживает перезагрузку — откат
   возможен только из бэкапа параметров. В приложении перед записью
   обязательно делается полный бэкап в `configs/`.
3. Номера строк в ссылках спецификации не совпадают с этим деревом
   (например, octaquad X указан как L941-955, фактически 993-1006) — причина в
   том, что спецификация ссылалась на другой слешок кода; содержимое совпадает.

### Исправление теста мотора

`AP_MotorsMatrix::_output_test_seq()` ищет мотор по `_test_order[i] == motor_seq`,
а `_test_order` — это третье число в таблице `MotorDef`. Для OCTAQUAD/X:
M1→1, M6→2, M4→3, M7→4, M3→5, M8→6, M2→7, M5→8.

Приложение теперь переводит выбранный мотор в номер теста через
`motor_mapping_core.test_order_for_motor()` и отправляет именно его в `param1`
(в журнале видно «Тест M6 (тест №2)»). Раньше отправлялся номер мотора, то есть
«тест M6» крутил бы M4 — идентификация дала бы неверный план.
